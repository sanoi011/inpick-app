# Step 2 사진·공간 부품·잠금 생성 개선 설계

기준일: 2026-07-22

## 목표

사진 기반 주거 프로젝트에서도 다음 진실성이 끊기지 않게 한다.

`사용자 사진/요구사항 → 실제 공간 유형 → 실별 디자인 → 부위별 SKU → 공종·수량·견적`

이미지 분석 실패는 견적 누락 사유가 아니다. 실패한 관측은 표준 가정값과 `현장 확인 필요` 상태로 대체하고, 성공한 관측 및 사용자 직접 선택은 우선 보존한다.

## 즉시 적용한 안정화 범위

1. 새 프로젝트는 이전 project id, Step 1/2 snapshot, 생성 이미지, 선택 상태, 견적/RFQ 임시 상태를 재사용하지 않는다.
2. 비동기 DB/이미지 복원이 늦게 끝나도 현재 활성 project id가 바뀌었으면 결과를 폐기한다.
3. 사진 기반 견적은 모든 이미지를 `전체 공간`으로 합치지 않고 `거실/침실/주방/욕실` 정체성을 유지한다.
4. Vision 결과가 없어도 실별 기본 SurfacePlan으로 17공종 견적을 생성한다.
5. 오피스텔 등 Step 1 주거 유형을 이미지 생성 프롬프트에 명시하고, 더 큰 아파트로 변환하지 못하도록 제약한다.

## 다음 구현 1 — 참조 사진 기반 공간 보존

현재 사진 모드의 신규 생성은 텍스트 프롬프트 중심이다. 사용자가 올린 원본 사진의 구조를 보존하려면 다음 파이프라인이 필요하다.

1. 원본 사진을 프로젝트 전용 private storage에 업로드한다.
2. 사진마다 `projectId`, `roomKey`, `residentialType`, `sourceImageId`를 저장한다.
3. 분석 결과를 두 층으로 분리한다.
   - 관측 사실: 개구부, 벽/바닥/천장 경계, 고정 가구, 카메라 방향, confidence
   - 사용자 요구: 유지/철거/교체, 원하는 스타일, 필요한 가전장
4. 이미지 생성은 text-to-image가 아니라 source image edit를 기본 경로로 사용한다.
5. 생성 프롬프트에는 다음을 fail-closed로 포함한다.
   - 오피스텔/원룸/투룸 등 주거 유형
   - 해당 실 이름
   - 원본 개구부 및 카메라 구도 보존
   - 확인되지 않은 방/창/문 추가 금지
6. 분석 실패 시 원본 이미지 + 사용자 프롬프트로 편집을 계속하되, 추론하지 못한 구조를 확정 데이터로 저장하지 않는다.

### 수용 기준

- 오피스텔 입력 결과가 아파트로 표시되거나 더 큰 주거 유형으로 승격되지 않는다.
- 생성 결과와 design output에 `sourceImageId`, `roomKey`, `residentialType`, `analysisStatus`가 남는다.
- 분석이 실패해도 원본 사진과 요구사항이 사라지지 않고 견적 단계로 전달된다.

## 다음 구현 2 — 주방 Assembly/SKU 선택

주방을 하나의 `싱크대` 품목으로 취급하지 않는다. 내부 모델은 최소 다음 부품을 독립 선택·견적화한다.

| 부품 코드 | 사용자 표시 | 견적 연결 |
|---|---|---|
| `base_cabinet` | 하부장 | 12-11 |
| `wall_cabinet` | 상부장 | 12-12 |
| `tall_cabinet` | 키큰장/팬트리 | 12-13 |
| `fridge_cabinet` | 냉장고장 | 별도 SKU line + 설치 |
| `kimchi_fridge_cabinet` | 김치냉장고장 | 별도 SKU line + 설치 |
| `countertop` | 싱크대 상판 | 12-14 |
| `sink_bowl` | 싱크볼 | 12-15 |
| `faucet` | 수전 | 12-16 |
| `hood_cooktop` | 후드·쿡탑 | 12-17 |
| `backsplash` | 미드웨이 타일 | 07-31 |

### 상호작용

- 정상 상태: 완성된 주방 assembly.
- 부품 선택 진입: 카메라 이동이 아니라 assembly 중심을 유지하면서 각 부품이 깊이·상하 방향으로 분리되는 explode animation.
- 부품 클릭: 해당 카테고리의 내부 `material_products` SKU만 표시.
- 선택 확정: assembly 상태, 렌더 편집 요청, SurfacePlan, 견적 line에 동일한 selection id를 기록.
- SKU 이미지/3D 모델이 없는 경우 3D 자산인 것처럼 표시하지 않는다. `2D 제품 이미지`, `재질 샘플`, `3D 모델`을 명확히 구분한다.

### 핵심 데이터

- `kitchen_assemblies`
- `kitchen_assembly_parts`
- `part_code`, `material_product_id`, `quantity`, `unit`, `dimensions`, `selection_source`
- `render_edit_id`, `surface_plan_id`, `estimate_line_ids`

### 수용 기준

- 각 부품 선택이 서로 덮어쓰지 않는다.
- 냉장고장과 김치냉장고장은 사용자 초반 선택 또는 주방 선택에서 독립적으로 포함/제외된다.
- 선택한 SKU가 이미지에 반영되지 못하면 성공으로 표시하지 않고 재시도/일반 규격 fallback을 구분한다.
- Step 3에서 모든 부품이 별도 line 또는 명시적 포함 line으로 나타난다.

## 다음 구현 3 — 전체 실 선생성, 거실 공개, 나머지 잠금

요구 UX:

1. 컨셉 확정 후 대상 모든 실의 low-quality preview generation job을 한 번에 생성한다.
2. 진행 화면은 `거실 → 주방 → 침실 → 욕실` 순으로 완료 상태를 보여준다.
3. 거실 결과는 즉시 공개한다.
4. 나머지는 생성이 끝나도 잠금 thumbnail만 보여주고 1토큰 사용 시 공개한다.
5. 공개는 재생성이 아니라 이미 완료된 결과에 대한 권한 해제다.

### 결제/보안 조건

단순 CSS blur는 금지한다. 원본 URL이 브라우저 응답에 있으면 결제 없이 열 수 있다.

- 잠긴 원본은 private storage에 둔다.
- 클라이언트에는 워터마크/저해상도 preview 또는 상태만 반환한다.
- unlock API가 토큰을 원자적으로 차감한 뒤 짧은 signed URL을 반환한다.
- 동일 결과 재공개는 중복 차감하지 않는다.
- 생성 실패 결과에는 차감하지 않는다.
- 생성 비용과 unlock 매출이 맞지 않으면 실 수/해상도/무료 범위를 조정하고 이중 차감하지 않는다.

### 수용 기준

- 사용자 한 번의 생성 요청으로 대상 실 전체 job이 등록된다.
- 실마다 생성 버튼을 다시 누르지 않는다.
- 잠긴 이미지 URL은 unlock 전 클라이언트에 노출되지 않는다.
- 거실은 공개, 다른 실은 개별 토큰 공개이며 재공개는 무료다.
- 일부 실 생성 실패가 성공한 실 결과와 견적 fallback을 지우지 않는다.

## 견적 완전성 규칙

실별 견적 조립 우선순위:

1. 사용자 직접 선택 SKU
2. 사진에서 확인된 부위/자재
3. 사용자 프롬프트에서 명시된 요구
4. 실 타입별 필수 공종/부품
5. 표준 fallback

각 line은 `source`, `confidence`, `assumptions`, `warnings`, `siteVerificationRequired`를 가진다. 분석 실패 때문에 line을 삭제하지 않는다. 대신 fallback line을 생성하고 UI에서 `이미지 확인`, `사용자 선택`, `표준 가정`, `현장 확인 필요`를 구분한다.
